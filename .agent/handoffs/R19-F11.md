# R19-F11 — T17 crash-window race verification

## Result

The full live `tests/system` suite passed ten consecutive `-race` runs through the SQS gateway and ten through the private direct MiniStack endpoint. Each run covered the commit-before-delete crash, observed the same message replay in a restarted process, checked queue deletion, and reconciled the wallet against its ledger.

## Diagnosis and change

- A baseline direct run failed once in ten runs because the harness started multiple application processes before waiting for any to bind its selected ephemeral HTTP port. Two processes selected port `35201`; the second exited at readiness with `bind: address already in use`. Starts now wait for readiness one at a time, and readiness failures are reported against the active subtest.
- The earlier R19-F1 marker/redelivery failure did not recur in ten unmodified gateway runs or the nine baseline direct runs that reached the crash scenario. Its historical cause cannot be established from those runs. R19-F7 had already given the crash scenario a fresh FIFO queue.
- The crash assertion previously checked only that a marker existed, that the inbox row was complete, and that approximate queue counts reached zero. It now matches the marker to the broker's returned message ID, requires a running process to be forcibly killed, waits for a restarted process to log an idempotent replay of that message, and reconciles the wallet after the final HTTP replay. These checks distinguish receive, durable commit, process termination, redelivery, and ledger state.
- During the first strengthened gateway run, the new log assertion reported a false failure: Fx formatted `messageId` and `idempotentReplay` inside the JSON `msg` string. The captured process log showed the correct replay. The helper now accepts both that observed format and structured fields.

Only `tests/system/multiprocess_test.go` changed; no production behavior or fault hook changed.
