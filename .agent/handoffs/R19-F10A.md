# R19-F10A — Concurrent replay inbox completion

## Change

- The idempotency unique-key fallback now completes an SQS message's inbox row in the same PostgreSQL transaction that reads the winning persisted result. `Execute` returns a replay only after that transaction commits, so the consumer can delete the SQS message after a durable inbox record exists.
- Shared replay inbox handling checks an existing message ID and payload hash, verifies its completed transaction link, and otherwise inserts and completes the row. Hash and external transaction ID conflicts still return before inbox completion.
- Added a PostgreSQL use-case race test that starts HTTP and SQS calls together with one operation/key, asserts one transaction and one ledger movement, checks the completed inbox link before replay, then verifies replay, inbox hash conflict, changed-operation hash conflict, and external-ID conflict behavior. Conflicts leave no inbox rows for those deliveries.

## Scope note

The new test exercises a real concurrent use-case race with PostgreSQL, including the SQS inbox identity. A valid same-operation race usually resolves at the wallet-lock recheck, so the database's unique-key fallback is not reliably forced by this test; the fallback itself now uses the same inbox completion function and commits before returning.
