### Column contract (for T06/T07)
- `wallets(id uuid, player_id text, currency char(3), balance_amount bigint, version bigint, created_at, updated_at)`. `updated_at` is set by trigger.
- `wager_transactions`: `id uuid`, `origin` (`INTERNAL`|`EXTERNAL`), `internal_key` (`'opening:'||wallet_id`, OPENING only), `provider_id`, `external_transaction_id`, `idempotency_key`, `request_hash` (lowercase hex SHA-256, 64 chars), `wallet_id`, `player_id`, `kind`, `round_id`, `game_id`, `amount bigint`, `currency`, `reference_external_transaction_id`, `reference_transaction_id` + `reference_kind` (resolved reference; set both or neither), `status`, `failure_code`, `failure_message`, `result_balance_amount`, `result_balance_currency`, `result_wallet_version`, `attempt_count`, `next_attempt_at`, `reference_deadline_at`, `lease_owner`, `lease_expires_at`, `created_at`, `updated_at` (trigger-maintained), `completed_at`.
- `ledger_entries(id uuid, wallet_id, transaction_id, wallet_version, direction CREDIT|DEBIT, amount>0, currency, balance_before, balance_after, created_at)`. `wallet_version` is the wallet version the entry produced, and `(wallet_id, wallet_version)` is the stable pagination order (REQ-053).
- `inbox_messages(consumer, message_id, payload_hash, transaction_id null, received_at, completed_at null)`, PK `(consumer,message_id)`.
- `outbox_events(seq identity, event_id uuid PK, aggregate_type, aggregate_id text, event_type, event_version, correlation_id, causation_id null, payload jsonb object, occurred_at, created_at, attempt_count, next_attempt_at, lease_owner, lease_expires_at, last_error, published_at)`.

### Rules the database enforces
- **Opening**: `OPENING` is `origin=INTERNAL`, status `PROCESSED`, amount > 0, no external fields; one per wallet (unique `internal_key` + partial unique index on `wallet_id`). A duplicate reports 23505 on either `wager_transactions_internal_key_key` or `wager_transactions_opening_wallet_key`.
- **External operations**: `provider_id`, `external_transaction_id`, `idempotency_key`, `request_hash`, `round_id`, `game_id` are all NOT NULL. `UNIQUE(provider_id, idempotency_key)` and `UNIQUE(provider_id, external_transaction_id)` (REQ-046/050).
- **Amounts**: `LOSS` amount = 0; `BET/WIN/REFUND/ROLLBACK/OPENING` amount > 0.
- **References**: REFUND/ROLLBACK require `reference_external_transaction_id`; WIN may carry one; BET/LOSS may not. Allowed targets: WIN→BET, REFUND→BET, ROLLBACK→BET|WIN|REFUND.
- **Reversals (REQ-040, D07)**: partial unique index on `reference_transaction_id` where `status='PROCESSED' AND kind IN ('REFUND','ROLLBACK')`. A BET can have one processed reversal of either kind, a WIN/REFUND at most one rollback, and rolling back a REFUND never reopens its BET.
- **PROCESSED dependents**: the referenced row must be PROCESSED and match wallet, player, currency and round; reversals must repeat its amount.
- **State**: terminal rows (`PROCESSED|REJECTED|FAILED`) cannot be updated or deleted (23001). Identity columns are immutable while pending. `REJECTED|FAILED` ⇔ `failure_code`. `PROCESSED` needs `result_balance_*` and `completed_at`. `PENDING|PENDING_REFERENCE` need `next_attempt_at`; `PENDING_REFERENCE` also needs `reference_deadline_at`. Terminal rows carry no schedule or lease.
- **Result and ledger (REQ-051)**: a `PROCESSED` non-LOSS transaction must have a ledger entry whose `balance_after` equals `result_balance_amount`, enforced at commit.
- **Ledger**: entries must extend the chain (the previous entry's `balance_after` equals this `balance_before`). Only OPENING produces version 1. The first movement of a zero-opened wallet is version 2 from balance 0. Amount, currency and direction must match the transaction. A ROLLBACK moves opposite to what it reverses. No ledger entry for LOSS.
- **Commit-time checks**: wallet `(version,balance)` must equal its ledger entry at that version, except the version-1/balance-0 zero opening, which has none. Each ledger entry must belong to a PROCESSED transaction and be reflected in the wallet.

## DECISIONS / ASSUMPTIONS
Answers from the Lead (via Orca ask):
- Ids: `wallet_id` and transaction ids are uuid. `player_id`, `provider_id`, external ids, `round_id`, `game_id` and keys are opaque non-blank text, 1–255 chars (`failure_code` ≤ 100), so T03/T04 must bound them at intake.
- `round_id`/`game_id` are required for every EXTERNAL operation. `wallet_id` is a NOT NULL FK, so unknown wallets are rejected at intake and never persisted.
- SQS operations must supply `data.idempotencyKey`; never use the messageId as the key.

My decisions:
- Money columns are `bigint` minor units plus `char(3)` currency; hashes are lowercase hex text, not bytea.
- `aggregate_id`, `correlation_id` and `causation_id` are text, to avoid constraining T03's event design.
- `ledger.wallet_version` is an addition to the brief, serving as chain link and pagination key.
- `wager_transactions.reference_kind` is a denormalised copy of the referenced row's kind (a composite FK guarantees it is true). It is what lets SQL restrict reversal targets.
- Leases are columns on `wager_transactions` and `outbox_events`, not a separate table.
- Error codes: all raised exceptions set `CONSTRAINT` so `pgconn.PgError.ConstraintName` identifies them; `schema.go` lists the names.

## KNOWN RISKS
- `TRUNCATE ledger_entries` is blocked, including via `TRUNCATE wallets CASCADE`. T15/T17 cannot truncate between tests, so use unique ids or recreate the database (`down` then `up`).
- The append-only and immutability guards are triggers: a table owner or superuser can disable them. The application role should not own the tables.
- BEFORE triggers run ahead of CHECK and FK constraints, so invalid ledger rows often fail with `ledger_entries_chain` or `ledger_entries_transaction_match` rather than the declarative constraint; map errors by SQLSTATE plus the `schema` constants, and treat 23514/23001 as programming errors.
- A wallet with version 1 and balance 0 is assumed to be zero-opened. Such a wallet can never have a ledger entry at version 1.
- The schema cannot validate that `request_hash` matches the canonical hash; T04/T06 own that.
- Wallet balance and its ledger entry must be written in the same SQL transaction, or the commit fails.

## NOTES FOR DEPENDENT TASKS
- **T06/T07 write order**: lock the wallet (`SELECT … FOR UPDATE`), then in one transaction insert the transaction row (`PROCESSED`, with `result_balance_*`, and `result_wallet_version` if you want it verified), insert the ledger entry with `wallet_version = wallet.version + 1`, and update the wallet `(balance_amount, version = version + 1)`. Statement order within the transaction does not matter, but the ledger entry must be inserted in version order. LOSS and REJECTED write no ledger and no version change.
- **Opening**: positive balance → insert wallet (version 1, balance N), OPENING transaction (`id` your choice, `internal_key='opening:'||wallet_id`, `result_balance_amount=N`, version 1) and ledger entry version 1 (CREDIT, before 0, after N). Zero balance → wallet only.
- **Replay**: look up by `(provider_id, idempotency_key)`; compare `request_hash`; return the stored `result_*`. A conflict on `(provider_id, external_transaction_id)` with a different key is the REQ-050 conflict.
- **Pending work**: claim with `WHERE status IN ('PENDING','PENDING_REFERENCE') AND next_attempt_at <= now() AND (lease_expires_at IS NULL OR lease_expires_at < now()) ORDER BY next_attempt_at, id FOR UPDATE SKIP LOCKED`; `wager_transactions_claim_idx` supports it. To find waiters when a reference arrives, query `(provider_id, reference_external_transaction_id) WHERE status='PENDING_REFERENCE'` (indexed). Set `reference_transaction_id` and `reference_kind` together when resolving.
- **Outbox**: claim with `WHERE published_at IS NULL AND next_attempt_at <= now() AND (lease_expires_at IS NULL OR lease_expires_at < now()) ORDER BY next_attempt_at, seq FOR UPDATE SKIP LOCKED` (`outbox_events_claim_idx`). Publishing sets `published_at` and clears the lease in the same UPDATE. Only delivery bookkeeping (`attempt_count`, `next_attempt_at`, lease, `last_error`, `published_at`) may change. Published rows may be pruned, unpublished ones may not.
- **Ledger pagination**: order by `(wallet_id, wallet_version)`; the cursor is the last `wallet_version`.
- **Reconciliation**: `SUM(CASE direction WHEN 'CREDIT' THEN amount ELSE -amount END)` over `ledger_entries` equals `wallets.balance_amount`, OPENING included.
- **Tests (T15/T17)**: run `migrations.FS` (or the files) with any golang-migrate-compatible runner; apply the `.up.sql` files in order.
