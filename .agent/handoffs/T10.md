IMPLEMENTED
- `internal/workers/reference` worker: claims due PENDING/PENDING_REFERENCE rows with `Store.ClaimTransactions` (SKIP LOCKED + lease), resumes each through `wagering.Service.RetryPending` (the only financial write path), and records the outcome. Pending state lives only in PostgreSQL, so a restart or a second instance picks it up (REQ-023, REQ-042).
- Exponential backoff, TTL/attempt exhaustion, stable codes and rejection events come from the domain/use case the worker drives: `Process` keeps the row PENDING_REFERENCE with backoff (1s base, 5m cap, doubling), then rejects with REFERENCE_NOT_FOUND (reference missing) or REFERENCE_UNRESOLVED (reference exists but still pending) once `RetryPolicy.Exhausted` (TTL or MaxAttempts) is true, emitting WagerTransactionRejected in the same commit (REQ-043, REQ-071). A reference that is REJECTED/FAILED gives REFERENCE_FAILED at once, with no further waiting (REQ-044).
- Double-apply protection, three layers: the claim is exclusive (SKIP LOCKED + lease); `RetryPending` re-reads the row under the wallet lock and treats a terminal row as a no-op (`Replay=true`, counted as STALE); DB constraints/triggers are the last line.
- `Config` + `LoadConfig` (REFERENCE_* env vars), `Worker.RunOnce/Run/Start/Stop`, optional `Observer` (Claimed, Attempted with result/failure code/duration) as the metrics hook for T13/REQ-076, and an Fx `Module` whose start/stop is bound to the lifecycle. Every call takes a context; each row has `ItemTimeout` (< `Lease`); `Stop` stops claiming, waits for in-flight rows, and cancels them if the Fx stop deadline passes (REQ-003, REQ-008).

DECISIONS / ASSUMPTIONS
- No new SQL and no change to pg/usecase: the worker reuses `ClaimTransactions` and `RetryPending`.
- The worker builds its own `wagering.Service` with `Config.Retry`, so backoff and expiry always follow the worker's config. The HTTP/SQS entry path (T08/T09) must build its Service with the same `reference.Config.Retry` (Fx provides `reference.Config`), otherwise the first backoff and the deadline written at entry would use another policy.
- Defaults: retry 1s/5m/24h TTL, no attempt cap (D08); batch 20, concurrency 4, lease 60s, item timeout 20s, poll 1s. Config requires ItemTimeout < Lease.
- A transient error on a row leaves its lease in place; the row is retried when the lease expires (no extra backoff state, no lease-release API was added to pg). Per-row errors are logged (transaction id and error only, no payloads) and never abort the batch.
KNOWN RISKS
- Retry after a transient/permanent error is at lease-expiry granularity (default 60s), and a persistently failing row is retried forever at that rate. A `ReleaseLease` with backoff or a dead-letter marker would need a pg change.
- If a lease expires while a row is still being processed, a second worker may record an extra reference attempt (attempt_count +1) before the first commits; the financial effect is never doubled. Keeping ItemTimeout well under Lease avoids this.
- Claims use DB `now()` while scheduling uses the application clock (Service.Now); clock skew between app and DB shifts retry timing by the skew. Tests override the schedule with SQL rather than sleeping.
- On shutdown, rows claimed but not started keep their lease until it expires (max `Lease`), then another instance takes them.
