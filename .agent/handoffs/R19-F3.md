# R19-F3 — Outbox backlog throughput

## STATUS

Complete. A publisher reclaims immediately after it records a successful publish, so the newly eligible next event for the same wallet does not wait for the polling interval.

## CHANGE

- `internal/workers/outbox/worker.go`: continue the claim loop after any successfully published event, including when SQL returned fewer than `BatchSize` rows. The existing full-batch shortcut and idle/error polling pause remain.
- `internal/workers/outbox/integration_test.go`: add a real PostgreSQL backlog case with six ordered events for one aggregate, a two-second polling interval, and a 1.5-second completion bound. Extend the two-publisher test to assert each aggregate's order as well as exactly one send per event.
- `internal/storage/pg/outbox.go`: unchanged. Its D31 `NOT EXISTS` predicate still admits only the earliest unpublished event per aggregate; `FOR UPDATE SKIP LOCKED` and lease predicates still prevent double claims. Publication still requires a committed outbox row, a live lease owned by the acking publisher, and the stored event ID.

## NOTES

An event whose send fails or whose acknowledgement is lost still blocks later events for that aggregate until retry or lease recovery. Successful publication opens the next claim immediately; another publisher may win that claim, but the SQL ordering gate still prevents overtaking.
