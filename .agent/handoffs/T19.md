## FINDINGS (most severe first)

### F-1 HIGH — Broker access control is not in effect; SQS can be used to impersonate any provider (SPEC §2, REQ-062, D12)
- Evidence:
  - `infra/localstack/init-sqs.sh:16-48` builds the queue policy through `jq -c .`, but the MiniStack image has no `jq`. Running `docker exec lead-localstack-1 which jq` prints nothing. The script has no `set -e`, so `set-queue-attributes Policy=""` runs and the script still reports success.
  - On the running stack, `aws sqs get-queue-attributes --attribute-names Policy` returns `"Policy": ""`.
  - The broker answers unsigned HTTP requests (`curl -X POST localhost:4566 Action=GetQueueAttributes…` → 200 with queue data). It also answers requests signed with arbitrary keys (`AWS_ACCESS_KEY_ID=attacker`).
  - The consumer trusts `data.providerId` from the message body (`internal/messaging/consumer/worker.go`, `ParseSQS` → `Execute`). It performs no producer/provider authorization.
- Impact: anyone who can reach the broker can submit BET/WIN/REFUND/ROLLBACK for any provider and wallet, which bypasses OIDC. D12 says "A política de broker impede provedores de publicar diretamente", which is false today. Even the intended policy (principal = account root) would grant everyone in the account the same access.
- Repair:
  - Generate the policy without `jq` (static JSON or the AWS CLI's `--attributes file://`), and fail the init script on error (`set -euo pipefail`).
  - Provision distinct producer and consumer identities with least-privilege statements, and enable credential enforcement in the emulator if it supports it.
  - Add an integration test that a non-authorized identity cannot SendMessage.
  - If the emulator cannot enforce IAM, state that explicitly as a limitation in ARCHITECTURE.md and correct D12.

### F-2 HIGH — A short PostgreSQL outage dead-letters valid wagers (SPEC §3 "indisponibilidade temporária do PostgreSQL", §10, REQ-022, REQ-065)
- Evidence: `init-sqs.sh:10` sets `maxReceiveCount=3`. Transient errors only set visibility to 1s, 2s, … (`worker.go:160-171`, `backoffSeconds` at :215). The consumer also keeps polling while the DB is down.
  - Measured with a real-broker probe that used the provisioned settings: a valid BET whose processing failed transiently ("connection refused") landed in the DLQ after **7.0 s and 3 attempts**. The probe was temporary and is not committed. It used the same harness as `tests/integration/sqs`.
- Impact: any PostgreSQL blip longer than a few seconds moves valid financial operations to the DLQ. Nothing redrives them, so they need manual intervention. The retry budget only fits poison messages, not "falhas transitórias exigem retry com backoff".
- Repair:
  - Size the receive budget for transient outages. For example, raise `maxReceiveCount` to 10–20, back off to the 300 s cap, and document the resulting outage window.
  - Pause receiving while readiness (DB ping) fails, so no receive counts are consumed during an outage.
  - Optionally provide a DLQ redrive procedure. Document the bounds (REQ-066).

### F-3 MEDIUM — Outbox throughput per wallet is capped at ~2 events/s, so lag grows without bound for an active wallet (SPEC §11/§12, REQ-068, REQ-076)
- Evidence: the claim (`internal/storage/pg/outbox.go:34`) admits only an aggregate's earliest unpublished event (`NOT EXISTS older … published_at IS NULL`). After a pass that is not a full batch, the publisher sleeps `PollInterval=500ms` (`internal/workers/outbox/worker.go:365`, `config.go:64`).
  - Measured on the Compose app: the four events of one wallet (open plus one BET) were published at +0.04 s, +0.55 s, +1.00 s and +1.52 s (`outbox_events.published_at - created_at`).
  - Each financial op emits 2 events, so a wallet doing more than about 1 op/s builds an unbounded backlog. Ordering and correctness are unaffected.
- Repair: once an event is published, let the same owner continue with that aggregate's next events while it holds the lease. For example, claim ordered runs per aggregate where no earlier event is leased by another owner, or loop immediately after any successful publish. Add a backlog test.

### F-4 MEDIUM — HTTP cannot tell a database outage from an internal error (SPEC §9 "indisponibilidade transitória … distinguíveis", REQ-055, REQ-022)
- Evidence: `internal/httpapi/api.go:151-170`. Pool/connection errors, serialization failures and `pg.ErrConcurrentUpdate` all fall into the default case and return `500 INTERNAL_ERROR`. `503 TEMPORARILY_UNAVAILABLE` is returned only when the *request* context was cancelled. `domain.ErrKindTransient` is defined but no storage error is ever mapped to it.
- Impact: clients cannot distinguish "retry safely later" from a server bug. The contract the spec requires is not met for the most common transient case.
- Repair: classify pgx connect/acquire errors, SQLSTATE classes 08/57P0x, and 40001/40P01 as transient. Return 503 with `Retry-After` and code `TEMPORARILY_UNAVAILABLE`. Add an HTTP test with the database stopped or the pool closed.

### F-5 MEDIUM — Required metrics are incomplete (SPEC §12, REQ-076)
- Evidence: `internal/observability/metrics.go`.
  - There is no outcome-by-status counter (PROCESSED/REJECTED/PENDING_REFERENCE/FAILED) for SQS and reference-worker results; only HTTP status codes are counted.
  - Outbox lag is accumulated only when an event is published. A stuck outbox reports no lag, and there is no gauge for unpublished backlog or oldest age.
  - Processing latency covers HTTP only, not SQS or worker processing.
  - "DLQ" counts redrive *candidates*, not DLQ arrivals.
- Repair: add a `wagering_transactions_total{status,source}` counter, a gauge for the oldest unpublished outbox age and count (queried periodically), and latency for the SQS and worker paths.

### F-7 MEDIUM (tests) — Spec-named concurrency scenarios lack direct evidence (SPEC §8, §10, §13; REQ-019, REQ-067, REQ-080)
- HTTP/SQS crossing in `tests/system/multiprocess_test.go:150-204` is **sequential**: HTTP commits first, then SQS delivers. No test races HTTP and SQS for the same operation (REQ-067 target "Cross-transport race test").
- "Independent wallets proceed" (`:131-148`) only shows that two BETs on different wallets both succeed. No test holds wallet A's row lock and shows that wallet B commits meanwhile, which is what "sem lock global" requires.
- The 80/80 scenario does not resend either BET afterwards ("Reenvios não podem alterar esse resultado").
- Repair: add these three assertions to the system suite.

### F-8 LOW — `SHUTDOWN_TIMEOUT` has no effect (REQ-003)
`internal/config/config.go:37` parses and validates it, but nothing applies it. `cmd/wagering/main.go:20` calls `fx.App.Run()` with Fx's default 15 s stop timeout. Pass `fx.StopTimeout(c.ShutdownTimeout)`, or drop the variable from compose and `.env.example`.

### F-9 LOW — API audience is Keycloak's built-in `account` client (REQ-059/060)
`compose.yaml:16` `OIDC_AUDIENCE=account`. Any realm token that carries the `account` audience passes the audience check. Authorization still needs the hard-coded `roles`/`provider_id` claims, so this is defence-in-depth only. Use a dedicated `wagering-api` audience mapper.

### F-10 LOW — Minor robustness gaps
- `internal/usecase/wagering/service.go:164-180`: the concurrent same-key fallback returns a replay without writing the SQS inbox row for that messageId. Financial idempotency still holds.
- `RetryPending` (`:202`) ignores lease ownership and `next_attempt_at`. A stale claimant can increment `attempt_count` early and shorten the attempt budget when `MaxAttempts>0`. There is no financial effect.
- Outbox has no attempt cap or parking. A permanently unpublishable event retries forever and blocks every later event of that wallet.
- The `POST /wagering/transactions` request log lacks the transactionId/walletId/externalTransactionId that are available (REQ-075).
- `go mod tidy -diff` is not clean: `aws-sdk-go-v2/credentials` is imported directly by tests but listed as indirect.

### Areas reviewed with no defect found
- **Money:** int64 cents, strict parser, overflow checks, currency mismatch. Float is used only for JWT `exp`/`nbf`.
- **Wallet and ledger invariants:** row lock plus a version-checked update, plus DB triggers:
  - The version steps with each balance change.
  - A ledger entry is required at commit (deferred constraint triggers).
  - The ledger is append-only, including a TRUNCATE guard.
- **Uniqueness:** `(provider,key)`, `(provider,externalId)`, one OPENING per wallet, one processed reversal per reference.
- **Execute flow:** idempotency replay and hash conflict both before and after the wallet lock. The provider is authorized before the use case runs, and reads and replays are provider-scoped (404 cross-provider).
- **Inbox:** inbox and financial commit are atomic, and delete happens only after commit.
- **Outbox:**
  - Leases use `SKIP LOCKED`.
  - Acknowledgement is guarded by owner and lease.
  - Per-aggregate order is enforced in SQL.
  - Republication keeps the same eventId.
- **Reference worker:** leases, TTL and attempt bounds, and stale-claim safety.
- **Shutdown:** HTTP stops first and PostgreSQL closes last. Workers stop claiming. Unstarted SQS receipts are released.
- **Domain package:** imports only the standard library.
