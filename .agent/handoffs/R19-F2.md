IMPLEMENTED
- `internal/messaging/consumer/worker.go`:
  - New `Worker.Ready` readiness probe (3 s bound). `RunOnce` probes before every receive; while it fails it returns `ErrDependencyUnavailable` and receives nothing, so an outage of any length spends none of the redrive budget.
  - `Run` logs one `SQS receives paused` warning per outage and `SQS receives resumed` afterwards (no per-poll error spam), polling the probe every `PollErrorDelay` (1 s).
  - After a transient failure inside a batch the probe is re-checked before each next message; if the dependency is down the unstarted messages are released unprocessed (visibility 0), not given an attempt each.
  - Transient failures keep exponential visibility backoff, now explicitly bounded by `Config.MaxBackoffSeconds` (default 60, was an implicit 300): 1, 2, 4, 8, 16, 32, 60, 60... s. DECISIONS / ASSUMPTIONS
- Gating on a PostgreSQL ping before each receive (instead of only backing off) is what keeps an outage from spending receives; the larger `maxReceiveCount` (15) and the 60 s backoff cap only bound the residual case where the database answers pings but commits keep failing.
- The Compose test stops (not pauses) the PostgreSQL container: a paused container hangs connections, so the in-flight attempt would simply wait and prove nothing about retries; a stop gives real "connection refused" failures.
- The Compose test cannot by itself tell old from new consumer code because `maxReceiveCount` is also raised; the in-process real-SQS tests carry that proof (they fail without the gate).
- The ping adds one cheap pool ping per receive cycle (every long poll, ~10 s when idle).

KNOWN RISKS
